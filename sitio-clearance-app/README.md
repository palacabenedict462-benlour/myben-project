# Sitio Clearance Ticket Service — Web App

This connects your original `clreance.py` console program to the HTML UI over
a real backend. `app.py` imports `clreance.py`'s `DatabaseManager` and
`PDFGenerator` classes directly and exposes them as a web API, and the
browser UI in `static/index.html` calls that API. The only change made to
`clreance.py` itself is a security fix to password hashing (see below) —
everything else in it is untouched.

```
sitio-clearance-app/
├── app.py              ← Flask API (imports clreance.py, adds HTTP routes)
├── clreance.py          ← your original program (password hashing hardened)
├── static/
│   └── index.html       ← the UI, wired to fetch() calls instead of mock data
├── requirements.txt
└── .gitignore            ← keeps the database, logs, and venv out of git
```

## 1. Install dependencies

```bash
cd sitio-clearance-app
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

`reportlab` is what powers the PDF certificate download — it's already in
`requirements.txt`, so PDF generation works without extra setup.

## 2. Run it

```bash
python3 app.py
```

Then open **http://127.0.0.1:5000** in your browser. The Flask server serves
the UI *and* the API from the same address, so there's nothing else to start.

The first run creates `clearance_system.db` (SQLite) and `clearance_system.log`
in this folder — same as when you ran `clreance.py` directly, since it's the
same `DatabaseManager.init_database()` doing the work.

## What's actually wired up

Every action in the UI hits a real endpoint and reads/writes the real SQLite
database — nothing is mocked:

- Sign in / sign out → session-based auth against `authenticate_user()`
- Submit a request → `save_clearance()`, generates the same `CL-YYYYMM-####`
  ticket number format as the console app
- Approve / reject / mark under review / mark released →
  `update_clearance_status()`, with role + sitio permission checks matching
  the console menu's rules
- Notifications → `add_notification()` / `get_notifications()` /
  `mark_notification_read()`
- Statistics → `get_statistics()`
- Reports → downloads real JSON exports (same shape as
  `export_clearances_json()` / `export_pending_json()`)
- Certificates → downloads a real PDF generated by
  `PDFGenerator.generate_clearance_certificate()`
- User management (admin) → `create_user()` / `get_all_users()`

## Using it from your phone

The server listens on all network interfaces (`0.0.0.0`), so any device on
the same WiFi as your computer can reach it.

1. Make sure your phone and computer are on the **same WiFi network**.
2. Find your computer's local IP address:
   - **Windows**: open Command Prompt, run `ipconfig`, look for "IPv4 Address" (e.g. `192.168.1.23`)
   - **Mac**: System Settings → Wi-Fi → click your network → look for the IP address (or run `ipconfig getifaddr en0` in Terminal)
3. Run `python3 app.py` as usual.
4. On your phone's browser, go to `http://<that-ip>:5000` (e.g. `http://192.168.1.23:5000`).
5. If it doesn't load, your computer's firewall may be blocking incoming connections on port 5000 — allow Python/Flask through it (Windows will usually prompt you the first time; on Mac check System Settings → Network → Firewall).

This only works while both devices share the same local network — it won't
work over mobile data or from outside your WiFi. For that, you'd need to
either deploy the app to a real server, or use a tunneling tool like `ngrok`
for a temporary public URL during testing.

## If you have an existing `clearance_system.db` from before

This update changes how passwords are hashed. `clreance.py` only inserts the
default accounts the *first* time (`INSERT OR IGNORE`), so an existing
database keeps its old-format hashes and won't recognize the new code. If
your logins suddenly stop working after updating, delete `clearance_system.db`
(and `clearance_system.log`, just to start clean) and restart — a fresh
database will be created with the new hashing automatically.

## Known limitations to be aware of

- **Password hashing**: now salted (PBKDF2/scrypt via Werkzeug) instead of
  the original plain SHA-256 — this was fixed directly in `clreance.py`'s
  `hash_password`/`authenticate_user`. If Werkzeug isn't installed (e.g.
  running `clreance.py` standalone with no dependencies), it falls back to
  a marked, still-unsalted SHA-256 scheme so the console app keeps working.
- **SECRET_KEY**: if you don't set a `SECRET_KEY` environment variable,
  `app.py` generates a random one each time it starts, which logs everyone
  out on every restart. Fine for local/demo use. For a real deployment, set
  `SECRET_KEY` yourself to a fixed, secret value (e.g. `export
  SECRET_KEY=$(python3 -c "import secrets; print(secrets.token_hex(32))")`).
- **Dev server + debug mode**: `python3 app.py` runs Flask's built-in
  development server with the interactive debugger on, which allows code
  execution if someone can trigger an error page. Fine on your own trusted
  WiFi; run with `FLASK_DEBUG=0 python3 app.py` to disable it, and use a
  production WSGI server (e.g. `gunicorn app:app`) for real deployment.
- **Single SQLite file**: fine for one barangay hall's usage; if you expect
  concurrent heavy write traffic, consider PostgreSQL down the line.
- **`.gitignore`** is included so `clearance_system.db`, `clearance_system.log`,
  and `venv/` never get committed — worth double-checking before your first
  push that none of these were already tracked from an earlier commit.
